# Android research

What the bridge app does today, what late-2026 Android practice is, and what is worth changing in a headless, privileged, single-screen app that places real SIM calls. Snapshot date: 2026-11-25. Everything below is grounded in `android/` as it exists here plus the linked primary sources; anything I could not confirm is marked **not verified**.

Effort scale: **S** ≤ half a day, **M** 1–3 days, **L** > 3 days (including the on-device verification each change needs).

Read for the "now" column: `android/build.gradle.kts`, `android/settings.gradle.kts`, `android/gradle.properties`, `android/gradle/wrapper/gradle-wrapper.properties`, `android/app/build.gradle.kts`, `AndroidManifest.xml`, `res/values/themes.xml`, `res/layout/activity_main.xml`, `res/xml/network_security_config.xml`, and the Kotlin sources under `app/src/main/java/com/phonxiety/bridge` (`BridgeEngine.kt` 1623 lines, `MainActivity.kt` 639, `PhoneAudio.kt` 634, `IrohLink.kt` 482, `CallLedger.kt` 359, `net/`), plus `magisk/` and the 13 JUnit 4 tests in `app/src/test`.

## Kotlin and language level

**Now.** Kotlin sources compile through AGP's built-in Kotlin. The build never pins a KGP version, so the compiler is whichever KGP AGP 9.5 declares a runtime dependency on (AGP 9.0 pinned 2.2.10; 9.5's value is **not verified** — `./gradlew buildEnvironment` shows it).

**Best practice.** Kotlin 2.4.21 is current; K2 is the only compiler. 2.4 stabilised context parameters, explicit backing fields, `@all`, the new annotation use-site defaulting and the `kotlin.uuid.Uuid` API ([What's new in Kotlin 2.4.0](https://kotlinlang.org/docs/whatsnew24.html), July 2026). AGP documents how to move above its bundled KGP: add `org.jetbrains.kotlin:kotlin-gradle-plugin` to the root `buildscript` classpath ([AGP 9.0 notes, "Upgrade to a higher KGP version"](https://developer.android.com/build/releases/agp-9-0-0-release-notes#android-gradle-plugin-built-in-kotlin)).

**Recommendation: adopt later (S).** Pin KGP 2.4.21 through the root `buildscript` so the compiler is explicit and reproducible, then leave the language level alone — nothing in this codebase wants context parameters or collection literals, and `BridgeEngine`'s `synchronized` blocks are a design issue rather than a syntax one.

## Gradle and AGP 9 build practices

**Now.** One module; versions are literals in `app/build.gradle.kts` (OkHttp 5.5.1, play-services-code-scanner 16.1.0, JNA 5.15.0, coroutines 1.9.0, JUnit 4.13.2); `gradle.properties` sets only `jvmargs`, `parallel`, `kotlin.code.style`; no configuration cache, no build cache, no convention plugins.

**Best practice.** Version catalogs are the documented Gradle mechanism for shared dependency versions and are what Android Studio scaffolds ([Gradle version catalogs, 9.6](https://docs.gradle.org/9.6.0/userguide/version_catalogs.html)). The configuration cache is *not* on by default and must be enabled with `org.gradle.configuration-cache=true` ([enabling the configuration cache](https://docs.gradle.org/9.6.0/userguide/configuration_cache_enabling.html)); Gradle 9.6 also improved cache reuse for properties passed via env/system properties, which matters here because the signing config reads `PHONXIETY_KEYSTORE*` from the environment. Convention plugins are justified by repeated module configuration — with a single module they add indirection for nothing ([sharing build logic](https://docs.gradle.org/9.6.0/userguide/sharing_build_logic_between_subprojects.html)). AGP 9 turns on `android.r8.strictFullModeForKeepRules`, `optimizedResourceShrinking` and a non-final R class by default, all of which only matter once minification is on.

**Recommendation: adopt (S).** Add `gradle/libs.versions.toml` + configuration cache now. **Skip** convention plugins and KSP — there is no annotation processing and one module. One caveat specific to this build when the cache is enabled: the signing block reads `System.getenv` at configuration time, which is a cache input (Gradle now tracks env reads precisely), so a keystore change invalidates configuration once instead of silently reusing the old store.

## UI: Compose, Material 3 Expressive, edge-to-edge, predictive back

**Now.** `MainActivity` is a plain `Activity` (not `AppCompatActivity`) with `setContentView(R.layout.activity_main)`: a `FrameLayout` → `ScrollView` with `clipToPadding="false"`, ~14 `findViewById` fields, and a 1 s `Handler.postDelayed` refresh that starts in `onResume` and stops in `onPause`/`onDestroy`. The theme is `@android:style/Theme.DeviceDefault.DayNight` with hard-coded `android:statusBarColor`, `android:windowLightStatusBar=true` and `windowLightNavigationBar=true`. No `fitsSystemWindows` anywhere.

**Best practice.** Compose 1.13 is stable under BOM `2026.11.01`, paired with Material 3 1.5.0, which graduates the expressive components (`ToggleButtons`, `WavyProgressIndicators`, `TimePickers`) and the `material3-ripple` artifact ([Compose November '26 release](https://developer.android.com/blog/posts/jetpack-compose-november-2026-release), 2026-11-18; [Material 3 1.5.0](https://m3.material.io/blog/compose-material-3-is-stable)). Adopting that BOM requires Kotlin 2.2+ and **compileSdk 37.1** — this project is on 37.0 ([Compose setup](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler)). Edge-to-edge is enforced from targetSdk 35 with no opt-out from targetSdk 36 ([edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge), [Android 16 changes](https://developer.android.com/about/versions/16/behavior-changes-16)); content must consume `WindowInsetsCompat.Type.systemBars()`. Predictive back animations are enabled by default at targetSdk 36 and `onBackPressed` is no longer called ([Android 16 changes](https://developer.android.com/about/versions/16/behavior-changes-16)).

**Recommendation: skip Compose (S for the insets fix).** One status screen with no lists and no navigation does not repay a toolkit migration, a few MB of APK and a compileSdk 37.1 bump; Compose is the recommended toolkit for *new* UI, not for rewriting a working 640-line screen. Predictive back needs nothing — the activity overrides no back handling. But the screen is currently drawn under the status/navigation bars with a theme that forces light icons in dark mode: call `WindowCompat.enableEdgeToEdge(window)` and apply `systemBars()` insets to the scroll view, and drop the hard-coded bar colours. That is a real, visible defect at targetSdk 37 and the cheapest fix in this list.

## Concurrency

**Now.** `BridgeEngine` owns `Executors.newSingleThreadScheduledExecutor` (link tick 1 s, playback emit 500 ms, dial expiry 5 s), two more single-thread executors (commands, DTMF), a `HandlerThread("phonxiety-callbacks")`, and roughly 40 `synchronized(lock)` blocks; `PhoneAudio` runs two raw `Thread`s at `THREAD_PRIORITY_URGENT_AUDIO` with `ReentrantLock` around decode. Coroutines exist only in `net/` (`IrohLink` uses `Dispatchers.IO` + `SupervisorJob` scopes, `suspendCancellableCoroutine`), pinned at 1.9.0 because iroh-ffi 1.2 was built against it. `MainActivity` polls `BridgeRuntime.linkState` once a second.

**Best practice.** Use coroutines and flows between layers, one serialised scope for mutable state, immutable `StateFlow` exposure, and lifecycle-aware collection ([architecture recommendations](https://developer.android.com/topic/architecture/recommendations), [coroutines best practices](https://developer.android.com/kotlin/coroutines/coroutines-best-practices)). Latest is kotlinx.coroutines 1.11.0 (2026-05-11), which is binary compatible with 1.9 ([releases](https://github.com/Kotlin/kotlinx.coroutines/releases/tag/1.11.0)).

**Recommendation: adopt, partially (M).** Replace the three executors and the `HandlerThread` with one `CoroutineScope(SupervisorJob() + Dispatchers.Default.limitedParallelism(1))` for engine state, expose link/call state as `StateFlow<LinkState>` and let the activity collect it instead of polling every second. Two hard exclusions, based on what the code actually needs: the audio threads in `PhoneAudio` stay raw threads at `URGENT_AUDIO` (a coroutine dispatcher cannot promise that priority, and `AudioTrack.write` blocking on a shared pool is how you get dropouts), and the `audio`-path `ReentrantLock` stays. `synchronized` on `lock` can become a `Mutex` only where the critical section never blocks on I/O; blocks that touch Telecom binders should stay as they are or move to the single-threaded dispatcher. Sizeable but mechanical; the payoff is that `LinkSupervisor`-style fakes become testable with `kotlinx-coroutines-test`.

## Serialization

**Now.** `org.json` hand-built objects: 45 `JSONObject` references in `BridgeEngine.kt`, 13 in `CallLedger.kt`, 3 in `BridgeConfig.kt`; every command is parsed field-by-field, and `JSONObject.NULL` is used explicitly.

**Best practice.** kotlinx.serialization 1.13.0 (2026-11-13, built on Kotlin 2.4.10) with `@Serializable` data classes and a configured `Json` instance ([releases](https://github.com/Kotlin/kotlinx.serialization/releases/tag/v1.13.0)). It is a compiler plugin, so it needs `org.jetbrains.kotlin.plugin.serialization` alongside built-in Kotlin (the same mechanism as the Compose compiler plugin, [setup](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler)); whether that combination is smooth on AGP 9.5 is **not verified**.

**Recommendation: adopt later (M).** The protocol has about a dozen command/event shapes (8 commands, 5 event types, replies) and the ledger a stable schema; typed models plus `ignoreUnknownKeys` would delete most of the manual `optString`/`optJSONObject` code and make framing tests cover message shape too. Do it in one pass with the wire format frozen (the daemon stays authoritative) and keep `org.json` out of the model classes. Not urgent: `org.json` is on the platform, works, and is already unit-tested indirectly.

## Persistence

**Now.** Plain files in device-protected storage, written atomically by `AppStorage.writeAtomically` (tmp file → `fd.sync()` → rename → directory fsync → owner-only mode), plus `migratePreferences` for the old `SharedPreferences` file. `BridgeConfig` and `CallLedger` are JSON; the iroh secret key is a raw file.

**Best practice.** DataStore 1.3.0 is stable (2026-10-21) and gives serialised, transactional, coroutine-based reads/writes over typed data with atomic replacement ([DataStore releases](https://developer.android.com/jetpack/androidx/releases/datastore#1.3.0)); it works inside a device-protected context. It replaces `SharedPreferences`, not hand-rolled crash-safe files.

**Recommendation: skip (—).** DataStore would not remove the thing that shapes this code: `BridgeService.onStartCommand` reads the pairing *before first unlock*, synchronously, on the service thread, and DataStore is suspend/Flow-first (the usual workaround is `runBlocking`). `AppStorage` already provides fsync + atomic rename + owner-only mode for a bounded document (`CallLedger` keeps at most 32 entries), and the iroh secret key must stay a raw file anyway. Revisit only if config or ledger ever need change observation or indexed queries — and then reach for SQLite/Room, not DataStore.

## Dependency injection

**Now.** None: `BridgeRuntime` is a process-wide `object` holding `@Volatile` engine/service references, and `BridgeEngine` constructs its own collaborators (`LinkSupervisor`, `PhoneAudio`, `CallLedger`).

**Best practice.** Constructor injection plus a container when a type is expensive or shared; Hilt is recommended only once a project has multiple screens with ViewModels, WorkManager, or back-stack-scoped ViewModels ([architecture recommendations](https://developer.android.com/topic/architecture/recommendations), [manual DI](https://developer.android.com/training/dependency-injection/manual), [Hilt](https://developer.android.com/training/dependency-injection/hilt-android)). Compile-time alternatives exist and are current — Metro 1.5.2 (2026-11-03, [repo](https://github.com/ZacSweers/metro)) and kotlin-inject (version **not verified**) — and both are Kotlin compiler plugins, i.e. another AGP-9-built-in-Kotlin compatibility surface.

**Recommendation: skip (—).** One module, one process, no ViewModels. `BridgeRuntime` is already the container; what it lacks is a testable seam, which the concurrency work above supplies by letting `BridgeEngine` take its dispatcher and clock. Adding Hilt or Metro to a 20-file app buys annotation processing risk for zero wiring saved. If DI is ever wanted, prefer constructor parameters over a framework.

## Telecom

**Now.** `TelecomManager.placeCall` with a `PhoneAccountHandle` extra (privileged `MODIFY_PHONE_STATE`), a non-UI `InCallService` (`BridgeInCallService`) bound under `CONTROL_INCALL_EXPERIENCE` from the Magisk privapp allowlist, call state read from `Call.Details`, hangup via `Call.disconnect()`, DTMF via `Call.playDtmfTone`, and audio taken from `AudioRecord(VOICE_DOWNLINK)` + `AudioTrack` to the telephony sink rather than the microphone.

**Best practice.** Jetpack `androidx.core:core-telecom` 1.1.0 went stable on 2026-11-04; it unifies `ConnectionService` and the transactional `TelecomManager#addCall` APIs, and its whole feature set — call extensions, network slicing, `CallControlScope#callTypeFlow`, self-managed audio routing — is aimed at **VoIP** apps that own both ends of the call ([core-telecom 1.1.0 notes](https://developer.android.com/jetpack/androidx/releases/core#1.1.0), [self-managed calls](https://developer.android.com/develop/connectivity/telecom/selfManaged)). I found no Android 17 Telecom behaviour change in either behaviour-change page.

**Recommendation: skip core-telecom (—).** This app is not a VoIP client: it dials a PSTN call over the SIM and taps the downlink/uplink of a call the platform owns. `core-telecom` would register it as a self-managed calling app, which is a different (and mutually exclusive) role, and none of its 1.1.0 additions apply. Keep the raw `InCallService` + `TelecomManager`, and treat `core-telecom` as the reference for audio-endpoint handling only. One thing worth copying from 1.1.0's changelog: it repeatedly fixes "audio routed to speaker instead of earpiece" and endpoint-revert races, i.e. that area is genuinely buggy at the platform level — so `PhoneAudio`'s explicit output-device selection (rather than trusting the default route) is the right call and should not be simplified away.

## Audio

**Now.** 48 kHz mono PCM16 RX from `AudioRecord` source `VOICE_DOWNLINK`; TX as 48 kHz stereo PCM16 `AudioTrack`, `USAGE_MEDIA`, explicitly routed to the telephony output device; both on raw `URGENT_AUDIO` threads with 20 ms framing; optional Opus via `MediaCodec` (`MIMETYPE_AUDIO_OPUS`) with hand-built `OpusHead`/pre-skip CSD; `AudioRecord.READ_NON_BLOCKING` and `AudioTrack.WRITE_BLOCKING`; handset mute through `AudioManager` flags with the previous state saved.

**Best practice.** `AudioTrack.Builder.setPerformanceMode(PERFORMANCE_MODE_LOW_LATENCY)` has existed since API 26 and is the documented way to ask for the fast mixer path ([AudioTrack.Builder](https://developer.android.com/reference/android/media/AudioTrack.Builder#setPerformanceMode(int))). AAudio is the low-latency native API, and Oboe wraps it with an OpenSL ES fallback ([AAudio guide](https://developer.android.com/ndk/guides/audio/aaudio/aaudio), [Oboe](https://github.com/google/oboe)). Android 17 adds background-audio hardening: while the app is not visible, audio playback and volume APIs are silenced unless a foreground service with while-in-use capability is running ([Background audio hardening](https://developer.android.com/about/versions/17/changes/bg-audio)).

**Recommendation: adopt the hardening audit (S); skip AAudio/Oboe; add `setPerformanceMode` (S).** The hardening audit is the highest-value item in this report and is covered below. AAudio and Oboe are for apps that own an output stream end-to-end — this one captures a downlink that only `AudioRecord`/`AudioSource.VOICE_DOWNLINK` (privileged `CAPTURE_AUDIO_OUTPUT`) exposes; AAudio's documented presets do not include a voice-downlink source (**not verified** that it is reachable at all through AAudio, and the NDK builder surface suggests it is not). `MediaCodec` Opus is fine here: 20 ms frames, synchronous dequeue, one instance per audio thread — replacing it with libopus would add a native dependency for no measured gain. `setPerformanceMode(PERFORMANCE_MODE_LOW_LATENCY)` on the TX `AudioTrack` is a one-line experiment worth taking, with the caveat that the telephony sink may not be on the fast path at all.

## Foreground services and Android 17 behaviour changes

**Now.** Three declarations: `BridgeService` (`specialUse`, `directBootAware`, exported behind `DUMP`, started from `MainActivity`/`BootReceiver`, with `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`, and holding the allowlisted `START_FOREGROUND_SERVICES_FROM_BACKGROUND` so a boot start does not depend on the broadcast's temporary allowlist), `BridgeInCallService` (`microphone`, bound by Telecom, calls `startForeground` in `onCreate`), and runtime `ACCESS_LOCAL_NETWORK` already in `Permissions.RUNTIME`.

**Best practice.** `specialUse` has no runtime prerequisite and no timeout, and needs the `<property>` subtype declaration this app already has ([FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types)). A `microphone` FGS cannot be created while the app is in the background unless an exemption applies — "a system component starts the service" is one, which covers Telecom binding `InCallService` ([background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start#wiu-restrictions-exemptions)). For Android 17, the while-in-use requirement is explicit: an app targeting 37 that touches audio in the background needs an FGS started with WIU capability, and the doc names system-initiated starts (for example by Telecom) among the ways an FGS acquires WIU ([Background audio hardening](https://developer.android.com/about/versions/17/changes/bg-audio)). Separately, targetSdk 37 has no local-network access without `ACCESS_LOCAL_NETWORK` ([Android 17 changes](https://developer.android.com/about/versions/17/behavior-changes-17)) — already declared and requested. Android 17 also adds per-app memory limits derived from RAM, reported as `ApplicationExitInfo` reason `REASON_OTHER` with `"MemoryLimiter:AnonSwap"` in the description — relevant to a process that must live for days ([all-apps changes](https://developer.android.com/about/versions/17/behavior-changes-all)).

**Recommendation: adopt the audit (S), then leave as is.** `BridgeService` is started from `BOOT_COMPLETED`, which is a background start: it is permitted but is *not* granted WIU. If at call time the only FGS the process holds were that one, Android 17 would silence `AudioTrack.write` with no exception and no log except `AudioHardening`. `BridgeInCallService` should carry WIU because it is created on a system binding — plausible from the docs but **not verified on device**. Test: `adb shell cmd audio set-enable-hardening throw`, place a call, check `adb dumpsys audio | grep AudioHardening` and that TX is audible; if it reports `level: full`, either start the microphone FGS from a visible app action or add a `mediaPlayback` FGS for the duration of TX. Also confirm nothing loads a native library from writable storage: targetSdk 37 requires `System.load()`ed files to be read-only (`UnsatisfiedLinkError` otherwise), which the current `extractNativeLibs=false` packaging satisfies ([Android 17 changes](https://developer.android.com/about/versions/17/behavior-changes-17)). No reflection and no `MessageQueue` internals are used, so the Android 17 lock-free `MessageQueue` and unmodifiable-static-final changes do not apply. `scheduleWithFixedDelay` is used, not `scheduleAtFixedRate`, so the Android 16 missed-period change does not apply either.

## Networking

**Now.** OkHttp 5.5.1 for the TLS WebSocket with a pinned trust manager, TCP_NODELAY set via an `EventListener`; iroh over uniffi-generated Kotlin bindings + JNA `@aar`; a custom 5-byte framing layer (kind + big-endian length, `Framing.kt`) over both transports; `network_security_config` forbids cleartext.

**Best practice.** OkHttp 5.5.1 is the current release (2026-10-22); 5.5.0 added opt-in Encrypted Client Hello support ([OkHttp changelog](https://github.com/square/okhttp/blob/master/CHANGELOG.md)). Ktor 3.6 is the current Ktor line ([what's new in 3.6](https://ktor.io/docs/whats-new-360.html)) and would only pay off if the code wanted a shared client abstraction across platforms. Android 17 enables ECH by default for targetSdk 37 apps whose networking stack supports it, and adds `<domainEncryption>` in the network security config to disable it per domain ([Android 17 changes](https://developer.android.com/about/versions/17/behavior-changes-17), [network security config](https://developer.android.com/privacy-and-security/security-config#domainEncryption)).

**Recommendation: skip Ktor; keep OkHttp; watch ECH (—).** Both transports are already libraries with thin adapters; swapping the WebSocket client for Ktor adds a second HTTP engine next to OkHttp for no benefit, and `net/network-research.md` already reached the same conclusion for framing. One new interaction to keep an eye on: ECH + this app's self-signed pinned TLS identity is untested (**not verified**) — if pairing starts failing against a daemon behind a tunnel after a targetSdk 37 device update, the first knob is a `<domainEncryption>` entry rather than an OkHttp downgrade. OkHttp 5.5 is already new enough to participate.

## Testing

**Now.** 13 JUnit 4 tests in `app/src/test/java/com/phonxiety/bridge/net` (7 framing, 6 link supervisor) using hand-written fakes and a manual clock/scheduler; `unitTests.isReturnDefaultValues = true` so `android.util.Log` stubs do not throw. No Robolectric, no instrumentation tests, no Compose tests.

**Best practice.** JUnit 5 still has no first-party Android runner; `android-junit5` provides one and documents AGP 8.2+, with AGP 9 support **not verified** ([android-junit5](https://github.com/mannodermaus/android-junit5)). Robolectric 4.18.1 (2026-11-18) supports SDK 37 ([releases](https://github.com/robolectric/robolectric/releases/tag/robolectric-4.18.1)). Roborazzi 1.79.0 (2026-11-12) is the screenshot-testing option on Robolectric native graphics ([releases](https://github.com/takahirom/roborazzi/releases)); the platform guide compares the host-side options ([screenshot testing](https://developer.android.com/training/testing/ui-tests/screenshot)). For flows, `runTest` + a test dispatcher is the documented approach ([test flows](https://developer.android.com/kotlin/flow/test)), Turbine for hot flows. The architecture guidance is blunt that layers should be tested with fakes, not mocks.

**Recommendation: adopt partially (S/M).** Keep JUnit 4 — 13 passing tests are not worth an unsupported plugin risk. Add `kotlinx-coroutines-test` and (optionally) Turbine together with the concurrency change, since that is what makes the engine testable; add Robolectric 4.18.1 only when `AppStorage`, `BridgeConfig` or `Permissions` need JVM tests, which is a real gap today (device-protected storage, atomic write and migration are untested). Skip Roborazzi and Compose UI tests: there is no Compose, and a screenshot of a status screen has no regression value for a headless bridge.

## Static analysis

**Now.** AGP's Android Lint with default settings; three `tools:ignore="ProtectedPermissions"` suppressions; no formatter or detekt; `kotlin.code.style=official` is set but nothing enforces it.

**Best practice.** Android Lint is the primary Android-specific check ([lint](https://developer.android.com/studio/write/lint)); turn warnings into failures for a build that ships by hand (`lint { warningsAsErrors = true; abortOnError = true }`) and use baselines for third-party noise. For Kotlin-specific rules, detekt 2.0 is still alpha (2.0.0-alpha.6, 2026-08-08) but is built against AGP 9.3.1 and has supported AGP 9 built-in Kotlin since alpha.3 — the 1.23.x line is stable but predates built-in Kotlin and will not analyse these sources ([detekt releases](https://github.com/detekt/detekt/releases/tag/v2.0.0-alpha.6), [compatibility](https://detekt.dev/docs/introduction/compatibility)). ktlint's 2.0 line is also alpha (`2.0.0-ALPHA-5`, 2026-11-23) and moved coordinates to `io.github.ktlint.core`; 1.8 is the last stable line ([changelog](https://github.com/ktlint/ktlint/blob/master/CHANGELOG.md)).

**Recommendation: adopt lint flags now (S); detekt later (S).** A privileged app that installs over itself via `adb install -r` has no store review to catch mistakes — `warningsAsErrors` plus a committed baseline is cheap insurance. Choose either detekt 2.0-alpha.6 or ktlint 2.0-alpha for style, not both, and only once the concurrency refactor settles; two alpha formatters on a 20-file project is churn.

## R8, baseline profiles, release hygiene

**Now.** `release` is unminified, undebuggable, signed with `PHONXIETY_KEYSTORE*` if present and the debug key otherwise; packaged as a Magisk module (`priv-app` + privapp allowlist XML + `customize.sh` API guard), with native libs kept uncompressed and 16 KB-aligned via `packaging.jniLibs.useLegacyPackaging = false`; `versionCode 3` in both `build.gradle.kts` and `module.prop`.

**Best practice.** R8 full mode is strongly recommended by the architecture guidance and is the AGP default when minification is on ([enable app optimization](https://developer.android.com/topic/performance/app-optimization/enable-app-optimization)), with `android.r8.strictFullModeForKeepRules=true` already the AGP 9 default. Baseline and startup profiles are recommended for startup latency ([baseline profiles](https://developer.android.com/topic/performance/baselineprofiles)).

**Recommendation: adopt R8 later (M); skip baseline profiles.** Minification would cut the APK (JNA `@aar` plus OkHttp dominate) but requires keep rules for JNA's reflective `Structure` mapping and for the uniffi bindings, and the only way to validate them is a full call on the device — so schedule it as its own change, not a build tweak. Baseline profiles target TTID/TTFD of an activity that is opened once during pairing; the app's real startup cost is the endpoint bind inside a service, which baseline profiles do not help. Two hygiene items that are worth doing regardless: fail the release build when `PHONXIETY_KEYSTORE*` is unset instead of silently signing with the debug key, and derive `module.prop`'s `version`/`versionCode` from the Gradle values so the pair cannot drift.
